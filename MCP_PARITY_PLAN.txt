0. TL;DR / DECISIONS
--------------------------------------------------------------------------------
- The "skill" of BloxBot is NOT a clever custom system. BloxBot points the
  OpenCode agent at ROBLOX'S OFFICIAL, BUILT-IN Studio MCP server (a local
  binary that ships with Studio). All the powerful tools (execute_luau,
  script_grep, multi_edit, start_stop_play, console_output, input simulation,
  inspect_instance, etc.) are implemented by ROBLOX inside that binary + the
  official Studio plugin. BloxBot just connects to it and writes a good prompt.

- The official server is open-source (MIT, github.com/Roblox/studio-rust-mcp-server)
  and documented at https://create.roblox.com/docs/studio/mcp . It uses the
  STDIO transport. On Windows it is launched as:
        cmd.exe /c %LOCALAPPDATA%\Roblox\mcp.bat
  On macOS:
        /Applications/RobloxStudio.app/Contents/MacOS/StudioMCP

- WHY IT IS FAST: everything is on localhost. The official Studio plugin
  long-polls a localhost HTTP bridge with IMMEDIATE re-poll after each response
  (no sleep between successful polls), so tool round-trips are ~1-5 ms.

- THE WEBSITE CONSTRAINT (the crux of everything):
  * The Roblox plugin (HttpService) can only make OUTBOUND requests. It cannot
    host a server the browser connects to.
  * A browser page served over HTTPS (apple-juice.online) CANNOT fetch
    http://localhost (mixed-content + Private Network Access blocking).
  * Today the web bridge round-trips through a REMOTE serverless KV (Turso) on
    apple-juice.online with a 150 ms poll loop + internet latency
    (~300-800 ms/call). That latency gap is the real performance difference.

- STRATEGY:
  * CLI  -> connect DIRECTLY to the official Roblox Studio MCP (local already).
           This is BloxBot's exact approach. Biggest, fastest capability jump.
  * WEB  -> (a) immediately: make the existing remote bridge localhost-grade
               fast (long-poll + blocking pop). No install. Helps everyone.
           (b) then: add a true-local path via a small local companion helper
               and AUTO-DETECT it (this is "Option D", described in detail in
               section 4). Power users get BloxBot-class speed; everyone else
               falls back to the optimized remote bridge.
  * TOOLS-> copy the official tool SURFACE/design (names, behavior) into our own
           plugin + MCP server so the web path reaches parity too.

- OPEN POLICY QUESTION (needs your call): execute_luau (arbitrary Luau) is the
  single biggest source of "skill." For the CLI it comes FREE (Roblox's server
  provides it and owns the safety model). For OUR web plugin we deliberately
  disabled loadstring/execute_luau for Roblox marketplace plugin safety.
  Re-enabling it in our plugin is a compliance decision, not a code one.

4. "OPTION D" EXPLAINED IN DETAIL — HYBRID LOCAL/REMOTE FOR THE WEBSITE
--------------------------------------------------------------------------------
WHAT IT IS (one line): the website automatically uses a FAST LOCAL path when a
small Apple Juice helper is running on the user's PC, and silently FALLS BACK to
the (improved) remote path when it isn't. Same UI, two transports, picked
automatically.

WHY WE NEED IT: a browser tab on https://apple-juice.online cannot talk to
http://localhost (mixed content + Private Network Access). And the Roblox plugin
can only make outbound HTTP — it cannot accept a direct connection from the
browser. So to get localhost speed on the web, SOMETHING local has to sit in the
middle. That "something" is a tiny helper process (we already ship executables:
dist/aj.exe, dist/aj-bg.exe, and kiro-proxy is basically this server already).

THE THREE PIECES IN OPTION D:
  1) The Studio plugin (unchanged role): keeps long-polling an HTTP endpoint for
     commands and posting results back. It just needs to be pointed at a
     localhost URL when local mode is active (it already supports a configurable
     Server URL field — defaulting to https://apple-juice.online today).
  2) The LOCAL HELPER (new/!reuse kiro-proxy): a small process on the user's PC
     that:
       - serves the HTTP bridge the plugin polls at http://localhost:PORT
         (localhost = ~1-5 ms round trips, exactly like the official server),
       - AND exposes a channel the browser can reach despite mixed content
         (options below),
       - relays: browser  <->  local helper  <->  plugin  (all on the machine).
  3) The WEBSITE: on load it PROBES for the local helper. If found, it routes all
     MCP tool calls through the helper (fast). If not found, it uses the remote
     bridge (works everywhere, just slower).

HOW THE BROWSER REACHES A LOCAL HELPER OVER HTTPS (the mixed-content fix):
  The blocker is that HTTPS pages can't call http://localhost. Ways around it,
  pick one (in rough order of robustness):
   (i)   The helper serves HTTPS/WSS with a certificate for a hostname that
         resolves to 127.0.0.1 (e.g. a *.apple-juice.online subdomain whose DNS
         A-record points to 127.0.0.1, with a real cert). Browser connects to
         wss://local.apple-juice.online:PORT which is loopback but cert-valid.
         (This is how some pro tools ship local bridges.)
   (ii)  Private Network Access: Chrome/Edge allow an HTTPS page to reach
         http://localhost IF the helper answers the PNA preflight
         (Access-Control-Allow-Private-Network: true) and proper CORS. Simpler,
         but support/*behavior* varies by browser/version — must feature-detect.
   (iii) WebSocket to ws://localhost from the HTTPS page — historically allowed
         in Chromium under PNA with preflight; also varies. Feature-detect.
         (Loopback is the special-cased origin.)
   Recommended: ship (i) as the reliable default; opportunistically try (ii)/(iii)
   to allow a zero-cert setup where the browser permits it.

DATA FLOW WHEN LOCAL MODE IS ACTIVE:
   Web UI tool call
     -> (wss/https to localhost helper)
       -> helper enqueues command in its in-memory localhost queue
         -> Studio plugin (long-poll on localhost, immediate re-poll) pulls it
           -> plugin executes in Studio, posts result to localhost helper
             -> helper pushes result back over the socket to the Web UI
   No internet hop. Latency ~ the official server.

AUTO-DETECT + FALLBACK LOGIC (what makes it "D"):
   on app start (and on a periodic heartbeat):
     probe = try connect to the local helper (short timeout, e.g. 500 ms)
     if probe.ok:  transport = LOCAL   (badge: "Local — fast")
     else:         transport = REMOTE  (badge: "Cloud")
   The agent-loop / studio-bridge call a single sendStudioTool(transport, ...)
   abstraction so the rest of the code doesn't care which path is used.
   If the local socket drops mid-session, transparently fall back to remote and
   show a non-blocking notice.

WHAT THE USER INSTALLS: nothing new conceptually — we already ship aj.exe /
aj-bg.exe and have kiro-proxy. We add a "local turbo" mode to that helper and a
one-time "point the plugin at localhost" toggle (or auto-config). Casual users
who never install the helper keep working via the remote bridge.

WHY NOT JUST DO LOCAL FOR WEB ALWAYS: because most web users won't install a
helper. D keeps the zero-install experience working (remote) while giving the
people who want maximum speed a path to it (local). Best of both, no regression.

Option D checklist (later — after Phase 1 & 2):
  [ ] add a "local turbo" HTTP+socket mode to the helper (reuse kiro-proxy)
  [ ] cert/hostname strategy for loopback-over-HTTPS (pick i; try ii/iii)
  [ ] plugin: easy toggle/auto-config to point Server URL at localhost helper
  [ ] web: local-helper probe + heartbeat + transport badge
  [ ] sendStudioTool(transport) abstraction in studio-bridge.ts
  [ ] graceful mid-session fallback local->remote

--------------------------------------------------------------------------------
 SUB-SECTION D.2 — STDIO→LOOPBACK BRIDGE (the safe alternative to tunneling)
--------------------------------------------------------------------------------
CONTEXT: A proposal surfaced to expose the official Studio MCP server remotely
via a public tunnel (ngrok / remote MCP gateway). REJECTED for the website — see
the rationale in part 3 below. The correct design keeps everything on the user's
machine: the Apple Juice helper wraps the official stdio server and serves it to
the dashboard over a LOOPBACK socket only. This is the implementation detail
behind Option D's "local helper" path.

1. ARCHITECTURAL STRATEGY
   [Roblox Studio Official MCP]
        ▲
        │ (local stdio / pipes)
        ▼
   [Apple Juice Local Helper]  ◄──(secure local loopback socket)──►  [Web Dashboard]

   The helper spawns the official Studio MCP server as a CHILD PROCESS and pipes
   its stdin/stdout. It exposes those capabilities to the dashboard strictly via
   the local loopback interface — never the public internet.

2. IMPLEMENTATION SPECIFICATIONS
   - BINDING: the helper's local server MUST bind to 127.0.0.1 (or a local IPC
     named pipe / Unix socket). It MUST NEVER bind to 0.0.0.0.
   - PROTOCOL TRANSPOSITION:
       * Inbound:  dashboard → local WebSocket → helper writes JSON-RPC to the
                   child process stdin.
       * Outbound: helper reads the child's stdout → pushes the JSON-RPC response
                   back over the local WebSocket to the dashboard.
   - The helper is a thin transposition layer; it does not interpret tool
     semantics — Studio remains the executor.

3. WHY PUBLIC TUNNELS ARE EXPLICITLY REJECTED
   - ATTACK SURFACE: an MCP endpoint grants arbitrary Luau execution + file
     read/write inside the live place. Public-tunneling it = internet-reachable
     RCE on the developer's machine. Loopback-only eliminates external discovery.
   - LATENCY: a tunnel routes client → internet → gateway → localhost and back,
     ADDING an internet round trip. Loopback avoids it — near-native speed, no
     internet hop. (Note: end-to-end latency still includes the Studio plugin's
     own poll cycle, so the win is "no internet hop," not literally sub-ms total.)
   - UX: no CLI tunneling tools, no third-party auth, no ephemeral URLs. The
     helper bundles into the app for a one-click "Connect" flow.
   - SUPPLY CHAIN: no piping code-execution rights through an unverified
     third-party gateway package.

4. ⚠️ TWO HARD REQUIREMENTS THE NAIVE DESIGN MISSES
   (loopback binding is necessary but NOT sufficient — both of these are
    mandatory, not optional hardening)

   4a. HTTPS → LOOPBACK IS BLOCKED BY DEFAULT (the real hard part)
       A page served from https://apple-juice.online cannot open ws://127.0.0.1
       or fetch http://localhost — mixed-content + Private Network Access (PNA)
       restrictions block it in Chrome/Edge. Binding to loopback does not change
       this. The bridge MUST ship ONE of:
         (i)  a loopback hostname with a VALID TLS cert (e.g. a subdomain whose
              DNS A-record points to 127.0.0.1) so the dashboard connects to
              wss://<host>:PORT that is loopback AND cert-valid; OR
         (ii) answer the PNA preflight (Access-Control-Allow-Private-Network:true)
              + correct CORS, where browser/version supports it (feature-detect).
       Recommended: ship (i) as the reliable default; opportunistically try (ii).
       Without this, the local path silently fails in the browser.

   4b. LOOPBACK IS NOT "TRUSTED" — DEFEND AGAINST LOCAL ATTACKERS
       127.0.0.1 stops EXTERNAL scanners but NOT other local code: any website
       the user visits, or any other app, can also reach 127.0.0.1. Without
       defense, a malicious web page can drive the bridge → full Studio RCE
       (classic DNS-rebinding / CSRF-against-localhost). The bridge MUST:
         - Validate the Origin header against a strict allowlist (only the Apple
           Juice dashboard origin[s]).
         - Require a per-session AUTH TOKEN minted by the helper and handed to the
           dashboard out-of-band (e.g. the user pastes/auto-pairs a code, or the
           helper opens the dashboard with the token); reject connections without
           it.
         - Validate the Host header (reject unexpected hosts → blocks DNS
           rebinding).
         - Bind to an ephemeral random port and/or use an OS pipe where possible.

5. D.2 CHECKLIST
   [ ] helper: spawn official Studio MCP as child, pipe stdin/stdout
   [ ] helper: loopback WebSocket server (127.0.0.1, ephemeral port or pipe)
   [ ] cert/PNA strategy for HTTPS→loopback (4a) — pick (i), feature-detect (ii)
   [ ] Origin allowlist + per-session token + Host validation (4b)
   [ ] dashboard: probe + handshake + token presentation
   [ ] graceful fallback to remote bridge when helper absent or handshake fails

--------------------------------------------------------------------------------
 REVISION R1 — ARCHITECTURE REVIEW DECISIONS (supersedes earlier ordering)
--------------------------------------------------------------------------------
Outcome of an architecture review. ACCEPTED items refine the design; the two
PUSHBACK items correct things that would bite during implementation. Where this
section conflicts with earlier text, THIS section wins.

ACCEPTED — R1.1  HELPER WRAPS THE OFFICIAL MCP; IT DOES NOT REIMPLEMENT MCP
  The helper must be a DUMB stdio<->loopback transposer around Roblox's official
  server — NOT a custom MCP that re-declares tools.
      DO:    aj runtime -> spawn mcp.bat -> pipe stdin/stdout -> expose JSON-RPC locally
      DON'T: browser -> AJ custom MCP -> Roblox plugin
  Rationale: owning tool definitions means owning compatibility bugs and every
  future Roblox MCP change. Wrapping = when Roblox adds new_tool_x, we get it for
  free. The helper does not interpret tool semantics. (This is exactly D.2 §1.)
  NOTE: this applies to the LOCAL/RUNTIME path. The WEB no-install path still
  needs our OWN plugin tool surface (Phase 3) because those users have no runtime
  and no official server reachable.

ACCEPTED — R1.2  WEB APP THINKS "TRANSPORT", NOT "MCP"
  Introduce a single abstraction the agent codes against:
      interface StudioTransport { callTool(name: string, args: unknown): Promise<Result> }
      implementations: LocalTransport (loopback helper) | RemoteTransport (cloud bridge)
  The agent calls studio.callTool("multi_edit", ...) and is ignorant of whether
  it is hitting Vercel, localhost, or stdio. This is the formalization of the
  earlier sendStudioTool(transport) note in studio-bridge.ts. Build this
  abstraction BEFORE wiring the helper so both paths drop in cleanly.

ACCEPTED — R1.4  SECURITY IS MANDATORY (reaffirmed, see D.2 §4b)
  Token flow chosen (NO copy-paste):
      aj runtime starts -> mints random per-session token
        -> opens browser to https://apple-juice.online/connect?token=xxxx
          -> dashboard stores token -> WebSocket handshake presents token
  Plus (from D.2 §4b): strict Origin allowlist (only the AJ dashboard origin),
  Host-header validation (anti DNS-rebind), ephemeral random port / OS pipe.
  Without these: "any website can control Roblox Studio." Non-negotiable.

ACCEPTED — R1.6  RENAME THE HELPER -> "APPLE JUICE RUNTIME"
  The helper is the foundation, not a one-off. Internally name it the
  Apple Juice Runtime:
      Apple Juice Runtime
        ├── Roblox MCP bridge (R1.1)
        ├── auth / token (R1.4)
        ├── updates
        ├── local cache
        ├── plugin connection
        └── future integrations (Blender, VS Code, Git, filesystem, ...)
  Target end-state architecture:
      AppleJuice Web
        │  detects local runtime
        ├── local mode  -> Apple Juice Runtime -> official Roblox MCP -> Studio
        └── cloud mode  -> API (remote bridge)
  Framing: we are NOT trying to beat BloxBot at AI. We MATCH its transport +
  tools (use the official MCP) and add our own UX. Shortest path to "why does
  this feel exactly like BloxBot?"

PUSHBACK — R1.3  HELPER ORDERING: PARTIAL DISAGREE (tradeoff, your call)
  Proposed: move helper before remote-speed + tool-parity.
  Caveat: the helper ONLY serves users who INSTALL the Runtime. It does not help
  no-install web users and does not remove the need for Phase 3 on our own
  plugin for that audience. Phase 2 (remote bridge speed) is CHEAP and helps
  EVERY existing web user with ZERO install, while the Runtime is the largest
  effort and still has an unsolved hard problem (R1.5 / D.2 §4a).
  This is a PRODUCT decision:
    - If "best experience = install the Runtime": helper early, Phase 3 shrinks
      to only what the no-install path needs.
    - If "no-install web must also feel like BloxBot": keep Phase 2 + Phase 3.
  RECOMMENDED ORDER (overruleable):
      1) CLI -> official MCP                         [DONE]
      2) StudioTransport abstraction (R1.2)          [small, unblocks both]
      3) Phase 2 remote bridge speed                 [cheap, universal, no install]
      4) Apple Juice Runtime (local helper)          [biggest win for installers]
      5) Phase 3 tool parity                         [scope to no-install needs]

PUSHBACK — R1.5  CERTS: DON'T TREAT AS OPTIONAL (correction to "avoid certs")
  Proposed: try http://127.0.0.1 + PNA first, cert "only if needed."
  Correction: an HTTPS page hitting ws://127.0.0.1 faces TWO INDEPENDENT blocks:
    (a) Private Network Access (PNA) — addressed by the preflight header, AND
    (b) MIXED CONTENT (secure page -> insecure ws/http) — a SEPARATE gate whose
        localhost behavior is murky and CHANGES between Chrome versions.
  PNA does not solve mixed content. So:
    - DO feature-detect and use the certless http/127.0.0.1 + PNA path as a fast
      path WHERE the browser allows it.
    - BUT the loopback-hostname + valid TLS cert path (D.2 §4a option i) MUST be
      built and ready as the GUARANTEED fallback — not "someday."
  Framing it as "avoid certs if possible" risks shipping something that works on
  the dev's machine and silently fails for a chunk of users. Cert path = the
  reliability backstop; certless path = the nice-to-have fast path.

--------------------------------------------------------------------------------
 REVISION R2 — PLATFORM REFINEMENTS (supersedes R1 build order)
--------------------------------------------------------------------------------
R2 keeps R1.3 and R1.5 exactly as written (the two pushbacks stand). It adds
capability negotiation, a high-level tool stance, and a pairing flow, and locks
the build order around the transport abstraction.

R2.1  TRANSPORT BECOMES A CAPABILITY PROVIDER (extends R1.2)
  The two worlds diverge in what they can DO, so the transport must advertise it:
      interface StudioTransport {
        callTool(name: string, args: unknown): Promise<Result>
        capabilities(): Promise<{
          tools: string[]
          executeLuau: boolean
          screenCapture: boolean
          inputSimulation: boolean
          local: boolean
        }>
      }
  Expected capability split:
      Local Runtime (official MCP): execute_luau ✅  inputSim ✅  screenCapture ✅
      Remote web (our bridge):      execute_luau ❌  inputSim ~  screenCapture ~
  USAGE — gate at BOTH layers (this is the part the naive version misses):
    1) CALL SITE guard:   if (caps.executeLuau) { use_debug_script() }
    2) PROMPT conditioning: negotiate caps ONCE per session and inject the
       available tool list into the agent's system prompt, so the model never
       PLANS around a tool it can't use and dead-ends a turn. Guarding only at
       the call site still wastes turns. Do both.
  Negotiate capabilities at session start; cache for the session.

R2.2  PHASE 3 IS "HIGH-LEVEL TOOLS", NOT "COPY ROBLOX 1:1"
  Roblox's MCP is a general-purpose Studio assistant surface. Apple Juice's goal
  is narrower: BUILD GAMES FASTER. So the official tools are the FOUNDATION/
  primitives, not the final UX. Target stack:
      Agent
        ├── high-level AJ tools   (build_feature, generate_system,
        │                          debug_gameplay_loop, balance_values,
        │                          explain_scene, ...)
        ├── official-compatible primitives (script_read, multi_edit, grep, ...)
        └── Studio
  NOT: Agent -> 500 tiny Roblox primitives -> Studio.
  OPEN DESIGN DECISION (decide before building Phase 3): are high-level tools
    (a) SERVER-SIDE ORCHESTRATIONS — real composite functions that call
        primitives in a loop on our side (testable, deterministic, more code), or
    (b) PROMPT-LEVEL MACROS — guidance that expands into primitive calls by the
        model (cheap, flexible, less predictable)?
  Likely answer: a hybrid (orchestrate the risky/multi-step ones; macro the rest)
  — but pick per-tool deliberately, don't default by accident.

R2.3  RUNTIME AUTH = PAIRING, NOT URL TOKEN (revises R1.4 token flow)
  Auto-opening /connect?token=abc can leak the token (browser extensions,
  antivirus URL inspection, another app observing the launched URL). Use a
  short-lived PAIRING flow instead:
      Runtime starts -> shows a pair code:   "Apple Juice Runtime — Pair: 483921"
      Browser: apple-juice.online/connect -> user enters the code
      -> Runtime <-> Browser establish the authenticated WebSocket
  HARDENING (mandatory — a 6-digit code is low entropy):
      - short-lived (e.g. expires in ~60-120s),
      - single-use (consumed on first successful pair),
      - attempt-limited (lock after a few wrong tries) to kill brute force,
      - still combined with the R1.4 Origin allowlist + Host validation + loopback
        binding. Pairing replaces the URL-token DELIVERY; it does not replace the
        other loopback defenses.

R2.4  LOCKED BUILD ORDER (supersedes R1.3's recommended order)
      1) CLI -> official MCP                         [DONE]
      2) StudioTransport abstraction (+capabilities) [MOST IMPORTANT MOVE]
      3) Remote bridge optimization (Phase 2)        [cheap, universal, no install]
      4) Apple Juice Runtime (local helper)          [biggest win for installers]
      5) Tool parity / high-level tools (Phase 3)    [scope per R1.1 note + R2.2]
  Why #2 first: every future feature then lands ONCE as studio.callTool(...),
  never as if(local)/else if(remote)/else if(cli) scattered across the agent.

R2.5  COMPETITIVE FRAMING (the thesis this whole plan serves)
  We do NOT try to beat BloxBot at AI. We MATCH its transport + tools (use the
  official Roblox MCP as infrastructure) and WIN on:
      - our prompts / agent loop
      - our UX
      - our game-building workflows (the high-level tools of R2.2)
  Final signed-off architecture:
      Agent
        └── StudioTransport
              ├── RemoteTransport -> Cloud MCP/bridge
              └── LocalTransport  -> Apple Juice Runtime -> Roblox Official MCP -> Studio
  MCP is infrastructure; the product is the agent + UX + workflows on top.

--------------------------------------------------------------------------------
 REVISION R3 — PHASE 2 CORRECTION: STORE IS TURSO, NOT REDIS
--------------------------------------------------------------------------------
Discovered during implementation: the KV layer is Turso/libSQL (src/lib/turso.ts),
NOT Upstash Redis. The KV interface exposes only get/set/del/expire/incr/decr/
sadd/srem/smembers — there is NO native blocking pop (BLPOP) or pub/sub. So the
earlier Phase 2 line "Redis LIST + BLPOP" is NOT available as written.

ACHIEVE THE SAME LATENCY WIN WITHIN TURSO:
  - SERVER-HELD LONG-POLL: hold the HTTP request open on /api/mcp/next (plugin)
    and /api/mcp/poll (MCP server) and INTERNALLY fast-poll the KV in a tight
    loop, returning the INSTANT data lands or after a bounded hold (~20-25s).
    This collapses the old "fixed 150ms client poll + full HTTP round trip per
    attempt" into a single held request — most of the perceived latency gain of
    BLPOP, without needing Redis.
  - ADAPTIVE RESULT WAIT: in awaitResult, fast initial interval (e.g. 60-80ms)
    that backs off — first response lands sooner without hammering the store.
  - QUEUE RACE: keep the JSON-array queue but the one-in-flight-per-session MCP
    pattern makes the read-modify-write race practically a non-issue; long-poll
    does not worsen it. (A true atomic dequeue would need a libSQL transaction;
    note as a future hardening, not required for the latency win.)
  - BACKWARD COMPATIBLE: long-poll must be OPT-IN via a query flag (e.g. ?wait=ms)
    so the EXISTING plugin (fixed 0.2s poll) keeps working unchanged; the plugin
    can adopt waiting later.
  - SERVERLESS NOTE: holding a request consumes a Vercel function invocation for
    its duration; cap the hold (<=25s, under the 300s route cap) and let the
    client re-issue. Acceptable for the bridge's low concurrency.
